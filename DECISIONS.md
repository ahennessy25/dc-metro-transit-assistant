# Decisions

Key design decisions made during implementation, newest first. Each entry is a decision plus a one-line reason why.

- **Missing-API-key handling as a distinct `ConfigurationError`**: `agent/core.py`'s `ask()` now checks `ANTHROPIC_API_KEY` up front and raises a dedicated `ConfigurationError` instead of letting the call fall through to the Anthropic SDK, which previously surfaced as a generic `TypeError` ("Could not resolve authentication method...") from deep in the SDK. This lets `app.py`'s `friendly_error_message()` show a specific "this deployment isn't configured" message (with instructions for `.env` vs. Space secrets) instead of relying on string-matching an SDK error message that could change across versions. `app.py` also now renders a banner at page load (not just after a question is submitted) when the key is missing, so the problem is visible immediately rather than only after a user tries the chat.
- **`respond()` de-duplication in `app.py`**: The file had two `def respond(message, history):` definitions — a leftover from a merge — where the second silently shadowed the first, so the ThreadPoolExecutor-based "thinking..." indicator and its ThreadPoolExecutor were dead code. Merged into one `respond()` that keeps the live-thinking generator behavior, `_clean_history()`, and the try/except error formatting together, and added guards for empty input and overly-long questions (`MAX_QUESTION_LENGTH`) so those short-circuit before spending an API call. The same bounded `ThreadPoolExecutor` (`max_workers=4`, mirrored in `ChatInterface(concurrency_limit=...)`) is the throttle against rapid repeated submissions rather than a separate rate-limiter, since a hackathon-scale Space doesn't need more than that.
- **Separate `eval/` question sets over extending `agent/verification_harness.py`**: The verification harness asserts on tool-routing (which tools got called), not answer quality — a case can call the right tool and still hallucinate a detail. Added `eval/akash_questions.py` as a distinct, human-graded (`good_answer_should` checklist, not automated pass/fail) question set so routing correctness and answer quality stay separately testable, and so multiple contributors can each add their own file without merge conflicts in one shared list.
- **`get_scheduled_times` first/last sampling**: `agent/tools.py`'s `get_scheduled_times` previously returned only the first 15 (earliest) scheduled times of the day via `.head(15)`, which meant a "what time's the last train" question could never be answered correctly — the data was truncated away before it got there. Surfaced by the Week 2 verification harness (`agent/verification_harness.py`, King St case). Fixed by sampling both the first ~8 and last ~8 times (`_first_and_last()`) instead of just the earliest ones; tool description updated to disclose this is a sample, not the full day's schedule.
- **`ask()` return shape**: `agent/core.py`'s `ask()` now returns `{"answer": str, "tool_calls": [{"name", "args"}, ...]}` instead of a plain string, so which tools were called (and with what arguments) is available to any caller — e.g. an eval harness — without needing to be extracted externally (logs, side effects). `tool_calls` accumulates across every round of the loop, including parallel tool calls within one round. This changed the return contract, so `core.py`'s own CLI block, `agent/manual_test.py`, and `tests/test_agent_core.py` were all updated to match.
- **Agent tool adapters**: `agent/tools.py` defines the 5 planned agent tools (CLAUDE.md's original list) as thin adapters over the real `data/` functions rather than pointing at the matching-signature stub files (`data/gtfs_static.py`, `data/gtfs_realtime.py`, `data/rag.py`), which exist but only `raise NotImplementedError`. Those three stub files are now dead code and should be deleted once nothing references them. Static GTFS is loaded once per process (module-level cache in `agent/tools.py`) rather than re-fetched per call, since `fetch_gtfs_static()` is too slow to call on every tool invocation and the data barely changes.
- **Caching layer**: `data/cache.py` uses lazy eviction (an expired entry is only cleaned up the next time `get()` happens to touch that key) instead of a background sweep thread, since a hackathon-scale cache never holds enough entries for stale ones to matter memory-wise, and it avoids thread-safety concerns entirely. Also note: both `Cache.get()` and the `@cached` decorator treat `None` as a cache miss, which is fine for WMATA/NWS calls (they return dicts/lists, never `None`) but would silently defeat caching on a function that legitimately returns `None`.
- **Test scope**: Unit tests (`tests/`, pytest) cover only the parsing/transformation logic in `data/wmata_static.py`, `data/wmata_realtime.py`, and `data/weather.py` — mocking `requests.get` and, for GTFS-RT, feeding real serialized protobuf through the parser. Live API calls and LLM output are deliberately not covered here: the `__main__` blocks already smoke-test the live calls, and conversational output is Week 3's evaluation harness. This is where WMATA is most likely to silently break us (a renamed field, a shifted protobuf structure) without an obvious error.
- **NWS User-Agent header**: Set to the GitHub repo URL rather than a personal email, since NWS requires an identifying header and the repo URL is more appropriate for a project that may be shared/demoed publicly.
- **Project scope**: Scoped to WMATA Metrorail only, not Metrobus. WMATA publishes these as separate GTFS feeds; only the rail feed has been integrated.
- **GTFS-Realtime parsing**: Using the `gtfs-realtime-bindings` library to parse WMATA's protobuf feeds, and converting results to plain Python dicts immediately in `data/wmata_realtime.py` rather than passing protobuf objects further into the app — keeps the rest of the codebase free of protobuf-specific handling.
- **Static GTFS storage**: Using pandas DataFrames (in `data/wmata_static.py`) rather than a local SQLite DB as originally planned, since DataFrames were sufficient for Week 1 development speed. Revisit SQLite once data volume or query patterns make repeated in-memory loading impractical.
